每条源动作先在指定变体上求解完整轨迹，再对全部原始地形逐一检验；不同地形不会被默认视为通过。拒绝变体不会出现在 `accepted` 子集。若后续对特定变体重新求解，使用新的 selections/run ID，保持其原始来源家族。当前先把全库每条轨迹和每个变体的实际结果做全，不能把失败状态伪装成全部合格。

PHP 文件不提供原始 mocap 基元家族的完整映射；参数化动作可能共享基元。因此当前保守按 gait 来源分组，并把合格子集列为 development，`train/validation/test` 为空且说明原因。不能仅按文件随机拆成 80/10/10 来声称独立泛化。

训练规模与策略验收不属于本次离线转换。转换进程仿真环境数为 0；GPU 的并行单元是独立轨迹与帧窗口，CPU 的并行单元是逐源动作的验收/标注任务。后续旧章节中“未实现/未开始”描述导入文档时的 pilot 基线，当前实现以本节和最新任务记录为准。

## 2. 现有求解器的实际行为

### 接触与任务空间目标

`selections()` 固定源文件和帧区间；`solve()` 仅接受 50 Hz、地形第 0 变体，并读取固定目录下的 G1 源标签。通过 G1 FK 和足底几何最低区域计算足底中心，依据距离与速度识别双脚支撑阶段：距离小于 9 mm，或距离小于 35 mm 且速度小于 0.35 m/s；填补短间隙并移除少于 4 帧的接触段。

支撑段采用足底位置中位数作为锚点，投影到地面/箱体顶面，足部姿态调整为 yaw 朝向。当前 `support_height()` 面向水平顶面，不能直接表示掌面接触墙侧面等场景。

身体参考以两机器人默认姿态校准，再应用固定 `1.25` 比例和 `dst.stand_height - 0.789` 根高偏移；躯干/末端姿态损失还使用 `[7,10,13]` 索引。这些是当前试验假设，需要替换为按模型语义计算和配置的映射。

### 优化与限制

求解变量为逐帧根部位置修正、旋转修正和 29 关节角。采用 Adam 与余弦学习率调度，损失包含足底位置/姿态、身体位置及部分朝向、脚部地形穿透、支撑贴面、时间平滑、关节速度和默认姿态正则。

当前优化中的地形穿透项只使用双脚采样点云；全身地形与自碰撞由事后检查器诊断，并没有对应的完整优化约束。关节角每步夹紧到限位内部；`neutral/clearance` 在更新后重新固定手臂，`tracked` 则保留臂部任务目标但尚未完成相应验收。

整段轨迹一次放入设备，按固定迭代数结束，没有收敛判据、长轨迹窗口、自动重试或优化状态恢复。当前 manifest 是逐片段直接重写，不能让多个 worker 共享输出目录。

### 质检和数据准入

几何检查使用 MuJoCo 编译后的碰撞几何，包括网格凸包，而非把视觉三角网格当作精确非凸碰撞表面。独立求距使用 `strict_reference=True`，不以求解器的脚部采样 loss 作为验收。

当前两对小腿—脚部凸包重叠保留原始结果与例外初筛；后续必须修复碰撞几何，或提供结构性排除的依据和版本记录。仿真关闭自碰撞不等于离线动作无自碰撞。

检查器目前没有“质检失败返回非零退出码”的批处理约定，筛选导出也不生成完整新 manifest。`make_labels` 不读取质量门槛，生成标签不意味着数据准入。`MotionLib` 已对天工的“没有有效地形变体”报错；但当前变体检查基于 body origin，高质量数据集仍需逐变体的实际几何验收。

以下为开发计划，尚无对应通用 CLI。初始实现应保留 pilot 作为回归参照，先完成代码和小样本验证，再决定是否运行全部 296 条。

| 阶段 | 输入与依赖 | 实现及输出 | 验收条件 |
|---|---|---|---|
| D1 通用任务与配置 | 现有源库、RobotSpec、来源清单 | 用配置指定源片段、帧区间、变体、机器人与求解参数；只扫描即可输出任务清单，未求解不创建动作产物 | 发现全部 296 条源动作；缺输入明确报错；原 7 片段选择可复现；任意新增片段不需改 `selections()` |
| D2 碰撞模型处理 | 冻结原资产、重叠报告；可与 D1 同期分析 | 保存碰撞对诊断；修正派生碰撞几何或记录有依据的结构性排除；更新模型身份 | 默认姿态及代表姿态有独立检查；不靠扩大阈值消除失败；受影响 FK/几何回归与标签失效路径明确 |
| D3 全身接触求解 | D1、D2；源全身轨迹及接触标签 | 按语义映射身体/尺度；接触阶段记录身体、表面、锚点与法向；统一 root+29 joints 求解，按类别配置脚、手及其他有效接触、全身穿透和自碰撞约束 | 合成约束案例正确；现有 7 片段回归；少量高台阶、手支撑和攀爬样本逐项报告误差和不可行原因 |

| D6 可恢复批量调度 | D1 任务清单、D4 恢复状态、D5 导出协议 | 每任务独立目录、资源绑定、原子提交、重试/跳过、失败继续、结果合并与运行统计 | 单卡/多卡输出覆盖一致；中断后不重复计入；不覆盖旧数据；改变代码/模型/配置会使相应缓存失效 |

### 通用数据契约的设计方向

- 继续使用目标模型的 canonical joint order、root wxyz、50 Hz 和 motion/terrain 文件约定；若未来要改变这些契约，独立版本化并验证消费者。
- 一条任务由源动作及帧区间、地形变体、目标模型和求解配置确定；保存输入哈希、代码版本和种子，不以易变路径作为唯一身份。
- 同一轨迹可逐变体检查。需要针对某变体单独重求解时，输出独立派生动作并记录原变体编号；同源动作的所有派生版本归入同一划分组。
- 当前 pilot `source_family` 是人工命名的原子动作标签，且 standing/stand 与 turning/left45 来自同一源文件；不能直接拿该字段做独立训练/测试划分。正式划分须建立源动作家族映射，沿用原迁移计划的固定种子 0 和按类别 80/10/10 目标；家族不足则标为开发数据/泛化不足。
- 分别记录求解完成、几何验收、动力学诊断和学习策略跟踪状态。报告必须包含未通过及未运行项；不能用 PD 单一结果替代学习策略可行性结论。
- 保留原地形位置和尺寸；确需改地形时另建数据版本，不能覆盖源 benchmark。

## 4. 算力与调度设计

本机在 2026-11-08 的会话检查中可见两张 RTX PRO 6000 Blackwell、每张约 96 GB 显存；这是环境快照，不是后续机器的固定假设。用户另提到双卡 5090，当前未接入或验证，作为可选额外计算节点。

首先实现“一条动作 × 一个变体 × 一组配置”的独立任务调度，每张 GPU 运行独立求解进程。现有 `--device` 可用于单个求解进程选择设备，但尚无队列、跨机器同步或统一结果收集。初期不引入单条轨迹的跨卡模型并行。

GPU 适合独立求解、参数扫描和少量困难动作验证；当前 MuJoCo 几何质检和 `make_labels` 主要使用 CPU。先测量每任务耗时、峰值显存和质量结果，再配置并行数；不能根据显卡数量预先声称线性加速。

跨机器运行须同步代码提交、环境、模型和输入哈希，分开输出后合并 manifest。默认先验证本机双卡，再增加其他机器。训练 OOM 另立诊断记录，不阻塞转换框架和离线工具开发，也不因增加 GPU 就视为问题已解决。

## 5. 分层验证与完成条件

| 层级 | 可以宣布完成的条件 | 仍不能推出的结论 |
|---|---|---|
| 源码开发 | D1–D6 接口及正常/错误路径实现，静态检查和必要测试通过 | 任意 PHP 动作都能求解 |
| 小样本算法验证 | 原 7 片段及新增代表类别有独立质量报告；复杂接触约束有正例和失败例；性能有测量 | 全量通过或独立泛化通过 |
| 全量转换 | 明确启动后，清单中所有任务都有成功/拒绝/失败状态，合格子集、标签、划分及汇总可追溯 | 所有 296 条必然可执行 |
| 策略跟踪能力 | 在冻结数据、模型和评估协议上完成 Stage 1 等相应验收 | 仅由参考视频或标签得出控制成功 |

后续测试优先覆盖真实风险：关节/坐标映射、固定链、接触切换和侧面法向；限位、穿透、滑动、超速与不可行接触拒绝；窗口衔接；源家族泄漏；中断恢复、输出冲突和身份失效。几何验收沿用 [usage 中的阈值](usage.md#4-独立质检与结果判读)，不可通过放宽门槛掩盖模型或标签问题。

历史回归入口为 [test_php_pilot.py](../../tools/test_php_pilot.py)、[test_robot_contracts.py](../../tools/test_robot_contracts.py)、[test_acp_pipeline.py](../../tools/test_acp_pipeline.py)。当前 pilot 测试依赖本地源库和 `php_pilot_v2/standing/stand_motion.npz`，新机器仅拉取代码无法直接运行全部测试；后续应补充独立可生成的小夹具。本轮仅整理文档，没有重跑这些实验或测试。

正式控制验收目标沿用[迁移计划 M5–M7](../tienkung3_29dof/migration_plan.md)：例如 M5 的站立 15 s、20 次复位无跌倒比例 ≥95%，启动集各片段 20 次复位成功率 ≥90%。这些是后续验收目标，当前尚未达成。
