# 224 球训练的执行效率优化

2026-11-10，用户观察 GPU 利用率约 30%，要求进一步提速。本次仅优化执行方式，不以放大 batch、减少更新次数或删减数据来提高利用率数字。

## 基线与候选

97 秒、每卡 97 次采样：GPU 0 平均利用率 35.9%，GPU 1 平均 32.2%；显存带宽利用率分别约 1.98% 和 1.11%；设备占用约 8223/7309 MiB。正式 224 球版本平均约 1.30 秒/轮。

奖励仍沿用密集几何阶段的 `reward_chunk_size=64`，每卡 128 个 imagination 起点 × 32 步 = 4096 个状态，被拆成 64 块，且每块反向时重算。224 球已经大幅缩小工作空间，因此测试 `reward_chunk_size=0`，一次处理全部 4096 行并保留激活。这个参数不改变样本量、loss 聚合、horizon、优化器更新次数或原生碰撞模型。

## 验证与测量方式

从五类动作各取一个源片段，129 个带扰动参考姿态，检查完整 PaperReward 和 soft termination 的输出，以及状态/动作梯度。0、64、256、1024 分块对照中输出完全一致，最大梯度绝对差 1.49e-8；包含不能整除的块尾，CPU FP32。证据 `evidence/reward_execution_equivalence.json`。

正式训练在 19:49 保存第 1000 轮完整检查点后停止，模型、优化器、归一化、课程与计数完整保留。同期只有测试服务运行，沿用 64/80 GiB 和共享 slice 保护。未更改转换 guard 或资源限额。

每个候选从同一个 `ckpt_001000.pt` 开始，完整 2960 个样本、512 环境、256/256 全局 batch、32 步 horizon、每轮 10/1/20 个 WM/policy/critic 更新不变。运行 75 轮，预热 25 轮后测量连续 50 轮；比较真实更新数、数值有限性、双卡状态一致性和显存峰值。候选训练权重与正式日志分开保存。

在原入口的诊断副本中加入 CUDA event / host wall 计时，只采样局部第 10–14 轮，先于正式测速窗口结束。分阶段时间为包含子调用的累计时间，不可将父项与子项相加；CUDA event 时间包含流上的等待/主机发射间隙，不表示 SM 的纯计算时间。正式训练入口尚未修改。

工具和证据：

- `tools/stage1_phase_profile.py`、`tools/bench_stage1_execution.py`：仅诊断运行的分阶段计时和顺序测试。
- `evidence/gpu_utilization_before_tuning.csv`、`evidence/execution_tuning_stop.json`。
- `evidence/execution_probe_config.json`、`evidence/execution_probe_systemd_command.json`。
- `logs/tienkung3_29dof/stage1_execution_probe_20261110/`：诊断入口、每个候选命令/日志/检查点、计时、验证结果。

## 对照结果与采用

| 相同全局配置 | 分块 64 + 重算 | 整批 4096 行，不重算 |
|---|---:|---:|
| 连续 50 轮平均秒/轮 | 1.30022 | 0.49781 |
| 相对速度 | 1× | 2.612× |
| GPU 0 / 1 设备峰值采样 | 8.030 / 7.137 GiB | 8.923 / 8.030 GiB |
| 测速窗口 WM/policy/critic 更新 | 500 / 50 / 1000 | 500 / 50 / 1000 |

两组完整 75 轮均完成：从源断点更新计数 10000/500/10000 到 10750/575/11500，检查点数值有限、无跳过，两卡状态哈希一致。每组实际只测一次 50 轮窗口，之后以正式训练窗口校准。

分阶段计时中，rank 0 的奖励正向约从 275 ms 降到 7 ms；policy_update 内所有 backward（含 critic）约从 700 ms 降到 83 ms。优化器与同步约 86 ms/轮，变化较小。分阶段工具有额外计时开销，且仅采五轮，不能把这些分项之和代替上表独立、未启用分项计时的 50 轮耗时。

20:00:46 已采用 `reward_chunk_size=0`，同一正式服务从原第 1000 轮断点恢复，测试权重未带入。生产控制器将原硬编码 64 改为读取配置、默认仍为 64；主训练入口、训练数据、算法更新规模没有改动。当前 launch_config.json 已重新绑定控制器哈希，旧配置和正式 benchmark/命令/参数均归档，新的源码快照为 `source_snapshot_unchunked.zip`。采用收据 `evidence/execution_tuning_receipt.json`。正式速度与剩余时间校准中。

## 正式续训校准

20:02:49，正式预热 25 轮后连续 50 轮用时 21.0721 秒，平均 **0.42144 秒/轮**；窗口更新仍为 WM/policy/critic 500/50/1000。已记录到第 1100 轮，日志全部有限，cgroup high/max/oom/oom_kill 均为 0。相比优化前 1.30022 秒/轮约快 **3.085 倍**。

当时剩余 58900 轮，按该窗口预计 **6.90 小时**，北京时间 **11 月 11 日约 02:57** 完成 60000 轮预算；评估另计，后续随运行速度滚动更新。正式值与诊断窗口 0.498 秒存在波动，因此保留两者证据，不以较快单轮代替完整窗口。

正式稳定运行期间再采样 77 秒，GPU 0/1 平均利用率分别 **48.77% / 41.30%**，设备占用约 **9128 / 8213 MiB**；此前 97 秒采样为 35.90% / 32.22%。平均功耗从 128.8/98.6 W 增至 146.4/114.9 W。使用同一主机及同一桌面环境，采样包含非训练设备占用，不能当作纯训练进程占用。

证据：`evidence/execution_tuning_formal_throughput.json`、`evidence/execution_tuning_formal_benchmark.json`、`evidence/execution_tuning_gpu_utilization.json`。GPU 利用率尚未满载，但执行冗余减少后吞吐提升大于利用率提升；后续关注完整训练吞吐与质量。
