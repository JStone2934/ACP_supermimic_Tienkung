## 执行安排

- GPU 0 采集 WM 数据、训练 WM，并更新 actor。
- GPU 1 收集完整物理回报并拟合 critic，与 GPU 0 的 WM 训练并行。
- GPU 1 保留可复用的完整轨迹缓冲区；无效、探索前缀和验证环境样本不进入 actor 训练。
- 传回 GPU 0 的数据只包含 critic 权重、优化器状态、诊断信息和预抽取的 actor 批次；不传输整段 MC 轨迹。
- 每个 actor 批次独立、有放回地从有效训练环境采样。预抽样不改变训练/验证分组。
- actor 更新前先派发旧策略评估，更新完成后派发候选评估。两次评估必须匹配旧策略摘要、版本、课程、种子及基线任务编号。
- 策略每 5 次更新执行一次物理检查。不合格时精确恢复 actor 参数及 Adam 状态。

## 计算与内存

用户随后要求采用标准 FP32。当前配置使用 `amp=none`、`allow_tf32=false`：
训练网络、参数、优化器状态、状态积分、几何、奖励和回报累积均使用 FP32。
矩阵运算精度设置为 `highest`，CUDA matmul 与 cuDNN 的 TF32 均关闭；运行服务额外设置 `NVIDIA_TF32_OVERRIDE=0`。
WM 损失、actor 单步展开和 GPU 1 critic 前向/反向使用 `torch.compile`；优化器使用 fused Adam。
actor 不使用 activation checkpoint，保留中间激活以避免反向传播时重复计算。
每个进程最多同时启动两个 Inductor 编译工作线程，限制首次编译的 CPU 和内存峰值。

完整 MC 轨迹使用预分配的 GPU 缓冲区和有效性掩码；critic 归一化按块更新，避免一次复制全部训练特征。
验证尾批次补齐到 1024 行执行，补齐部分不计入验证误差。
正式验收使用 FP32 actor，与导出的 FP32 actor 一致。

主机、PHP guard 和 PHP 服务配置不变。按用户最新要求，训练服务不再设置单独的内存或交换空间上限，
MemoryHigh / MemoryMax / MemorySwapMax 均为 infinity，统一受主机现有保护管理；运行时长无限制。
容量按估计选择，未声称经过 4096/1024 容量或吞吐基准测试。

## 2026-11-14 内存退出修复

21:27:30 的退出由 systemd-oomd 发出 SIGKILL，发生在第 1595 轮的正式评估过程中。
原训练服务的 24 GiB 软限制会产生直接回收压力。复现发现：反复构造临时仿真器时，
CUDA 图相关的循环资源没有及时回收，单进程驻留内存从约 10.4 GiB 增至 15.6 GiB；
显式 GC 后降至约 12.0 GiB。修复构造过程的回收后，同样序列结束时约 10.6 GiB。

正式评估与 WM 验证现在复用各自的仿真器，每次重置所有场景及上下文；课程导致场景数改变时，
先释放旧正式评估仿真器再创建新实例。1500 控制步、初始帧、失败场景和全部验收条件保持原样。
每次工作任务输出仿真器创建次数与内存记录；训练另每 5 秒写入 `train/memory.jsonl` 和 `memory_latest.json`。

正式评估开始前保存 pending 状态，异常恢复时先补做未完成评估；旧第 1595 轮检查点也能识别应补做的评估。
服务使用 `tools.run_aiming_physical_service`，每次启动读取最新 `train/last.pt`，不重复使用最初的恢复快照。
异常退出后等待 30 秒重启，30 分钟最多允许 3 次服务启动，反复故障会留下明确的失败记录。
这属于故障重试保护，不限制正常训练的轮数或时长；显式停止和正常完成不会被自动拉起。
